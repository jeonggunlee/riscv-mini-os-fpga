# ZCU104에서 RISC-V + Mini OS 실행

## 구성

ZCU104의 `xczu7ev-ffvc1156-2-e` **PL**에 RV32I CPU, 8 KiB
프로그램/데이터 RAM, 별도 8 KiB MiniFS RAM disk, timer, UART 송신기를 구현한다. 내장 ARM(PS), DDR,
Linux, FSBL은 이 데모의 실행에 사용하지 않는다. Nexys A7용 파일은 유지한다.

```text
보드 300 MHz 차동 클럭 → IBUFDS → BUFG → /24 → BUFG → 12.5 MHz
                                                     ├─ RV32I + RAM + timer
                                                     └─ UART serializer
Mini OS: boot.S → kernel_main → timer/ECALL → trap.S → 다음 태스크 → MRET
UART: FPGA C19 → FT4232 채널 D → USB → PC
```

CPU와 UART가 같은 클럭을 사용하므로 ready/valid에 별도 CDC가 없다.
UART는 115200, 8 data bits, no parity, 1 stop bit, 흐름 제어 없음이다.
실제 정수 분주 값은 108이며 baud는 약 115741(+0.47%)이다.
CPU timer tick은 125000 clocks, 즉 약 10 ms이다.
부팅 직후 자동 reset이 적용되며 **SW20**을 누르면 Mini OS만 재시작한다.
SW20은 active-high이다. PS reset 버튼과 혼동하지 않는다.

## 핀 및 공식 자료

| top 포트 | FPGA 핀 | 전기 규격 | 역할 |
|---|---|---|---|
| CLK_300_P/N | AH18 / AH17 | DIFF_SSTL12 | 기본 300 MHz 보드 클럭 |
| CPU_RESET | M11 | LVCMOS33 | SW20, active-high |
| UART_TX | C19 | LVCMOS18 | PL → USB, 채널 D |
| LED[0..3] | D5 / D6 / A5 / B5 | LVCMOS33 | heartbeat / reset 해제 / UART busy / PC[8] |

핀은 [UG1267](https://docs.amd.com/api/khub/documents/g76en4BfB6qIp2gHDRkQxg/content)의
회로도, 표 3-18, 3-24 및
[공식 보드 XML](https://github.com/Xilinx/XilinxBoardStore/blob/2022.1/boards/Xilinx/zcu104/1.1/part0_pins.xml)로 확인했다.
300 MHz 핀과 전기 규격은 공식 보드 XML을 따른다(구버전 UG1267 표 3-13과 다름).
UG1267 표 3-18의 FTDI DDBUS 번호 열은 그림 3-13과 뒤바뀌어 있다.
회로도와 보드 XML 기준 **C19가 FPGA 송신, A20이 FPGA 수신**이다.
UART bank 28은 1.8 V이므로 Nexys의 LVCMOS33을 그대로 쓰면 안 된다.

## 실행 순서

프로젝트 루트에서 다음을 실행한다. Vivado 및 RISC-V GCC가 PATH에 있어야 한다.

```bash
# 기존 SoC 기능 검증
make sim-c-demo
make sim-mini-os

# 새 top / 실제 UART 직렬 파형 / 자동 reset / warm reset 검증
make sim-zcu104

# 고정된 10 ms tick으로 펌웨어를 재컴파일하고 합성·배치배선·bitgen
make vivado-zcu104

# UART를 먼저 열고 PL 다운로드 후 실제 출력 자동 검사
make test-zcu104

# UART 검사 없이 다운로드만 하는 경우
make program-zcu104
```

`make test-zcu104`는 연결된 장치에 **실제로 다운로드**한다.
JTAG로 volatile PL만 교체하며 QSPI/SD/ARM 펌웨어를 쓰지 않는다.
검사기는 부팅 배너, MiniFS 데모의 PASS, A/B/C 출력, 문자 전환,
잘못된 UART 바이트가 없는지를 검사한다.
이것은 실제 동작 smoke test이며 모든 레지스터나 IRQ 횟수를 보드에서 직접
관측하는 검사는 아니다. IRQ 및 ECALL 카운트는 RTL 시뮬레이션에서 검사한다.

### 입력 가능한 Mini Shell

Mini Shell은 별도의 16 KiB 프로그램/스택 RAM 이미지를 사용한다. UART RX는
FPGA A20 핀을 통해 같은 FT4232 채널 D로 들어가며 64바이트 하드웨어 FIFO가
있다. A/B/C 연속 출력 태스크는 이 이미지에서 실행하지 않는다.

```bash
make sim-shell              # RTL UART RX + 명령 파서 + MiniFS 검사
make vivado-zcu104-shell    # build/zcu104_shell/zcu104_mini_shell.bit 생성
make test-zcu104-shell      # 실제 PL 다운로드 후 명령 자동 입력·응답 검사
```

직접 입력하려면 `make program-zcu104-shell`로 다운로드하고 같은 채널 D를
115200-8-N-1 터미널로 연다. `help`, `ls`, `cat <file>`,
`write <file> <text>`, `rm <file>`을 사용할 수 있다. 예:

```text
rv> write hello.txt Hello
written
rv> ls
hello.txt  5 bytes
rv> cat hello.txt
Hello
rv> rm hello.txt
removed
```

셸은 한 줄 최대 95자, ASCII 입력·Backspace·CR/LF를 지원한다. `write`는
파일 전체를 교체한다. 출력의 개행은 터미널 커서가 첫 칸으로 돌아가도록
CRLF(`\r\n`)로 보낸다. `cat`은 64바이트씩 나눠 읽는다. 파일 데이터는 전원
차단과 FPGA 재구성 시 사라지지만 SW20 CPU reset에서는 유지된다.

2026-09-29 실제 보드에서 `make test-zcu104-shell`을 실행해 172바이트의
UART 응답을 수신했다. `write hello.txt Hello` → `cat hello.txt` → `ls` →
`rm hello.txt` → `ls`가 모두 통과했고, 마지막 목록에서 파일이 사라진 것도
확인했다. Vivado DRC 오류는 0, setup/hold slack은 각각 +2.629/+0.034 ns였다.
검증한 bitstream SHA-256은
`ba19708eb15e1642e8726b610e08911171efe2dd270d9351aebcb7b2e1f85ca3`다.

줄바꿈을 CRLF로 통일한 후 다시 생성한 bitstream은
`build/zcu104_shell/zcu104_mini_shell.bit`이며 SHA-256은
`cdb51db3cfb81efe1f38376adcc5f9ba228408a2e5c7965b2a27c44cfa9695b2`다.
RTL 시뮬레이션과 Vivado 타이밍·DRC가 통과했다. 기존 detached `screen`
세션을 종료한 뒤 `make test-zcu104-shell`로 실제 보드에 다시 다운로드해
`write`, `cat`, `ls`, `rm`, `ls` 명령을 검증했다. 176바이트를 수신했고
검사는 `passed: true`였다. 수신 데이터의 모든 줄바꿈은 `0D 0A`(CRLF)로
확인했다.

보드가 여러 개면 다음처럼 케이블 및 UART를 모두 명시한다.

```bash
HW_TARGET='*/Xilinx/46635A' python3 scripts/test_zcu104_uart.py \
  --port /dev/serial/by-id/usb-Xilinx_JTAG+3Serial_46635-if03-port0 --program
```

시리얼 접근 권한과 Vivado cable driver가 필요하다. 다른 터미널이 해당 UART를
읽고 있으면 닫고 실행한다. 채널 D는 이번 연결에서 `/dev/ttyUSB3`이지만 USB
열거 순서가 달라질 수 있으므로 `by-id` 경로를 권장한다.
`--program`을 빼면 다운로드하지 않고 수신만 한다. 이때는 수신 중 SW20을 눌러
부팅 배너를 다시 출력해야 한다.

## 산출물

| 파일 | 내용 |
|---|---|
| build/zcu104/zcu104_mini_os.bit | Mini OS RAM 초기값을 포함한 비트스트림 |
| build/zcu104/build.log | Vivado 전체 빌드 로그 |
| build/zcu104/timing_summary.rpt | setup / hold / unconstrained 검사 |
| build/zcu104/utilization_route.rpt | 최종 FPGA 자원 사용량 |
| build/zcu104/drc.rpt | 물리·전기적 설계 규칙 검사 |
| build/zcu104/hardware_program.log | 자동 테스트의 JTAG 프로그래밍 로그 |
| build/zcu104/uart_capture.bin | 실제 수신한 원본 바이트 |
| build/zcu104/uart_result.json | 배너·태스크별 문자 수·검사 결과 |
| build/zcu104_serial.vcd | board-top 시뮬레이션의 TX/reset/LED 파형 |

빌드 스크립트는 setup 또는 hold slack이 음수이면 bitgen 전에 중단한다.
비동기 버튼과 UART/LED 출력만 외부 동기 타이밍 검사에서 제외하며,
CPU와 RAM 내부 경로는 제외하지 않는다.

## 현재 제한

- ISA/OS는 기존 교육용 구현 그대로이며 M-mode만 사용한다. 메모리 보호가 없다.
- 프로그램/데이터 RAM 8 KiB와 RAM disk 8 KiB는 모두 distributed RAM이다.
- UART RX 및 호스트 명령 입력은 구현하지 않았다.
- timer MMIO는 하위 32-bit만 제공한다. **약 343초(5분 43초) 이후에는
  기존 timer wrap 문제가 발생할 수 있으므로 장시간 실행용 OS는 아니다.**
  테스트를 다시 하려면 SW20으로 reset한다. 상위 word MMIO와 안전한 64-bit
  비교값 갱신은 별도 개선이 필요하다.
- 전원을 끄면 PL 구성은 사라진다. 다음 전원 인가 후 다시 다운로드해야 한다.
- 클럭 발생기는 보드 기본 300 MHz 설정을 전제로 한다.

## 실제 검증 기록 (2026-09-27)

아래 표는 **MiniFS 추가 전 펌웨어**의 기록이다. MiniFS를 포함한 새 버전의
실제 보드 결과는 이어지는 2026-09-29 기록을 참고한다.

연결된 케이블 `46635A`, FPGA `xczu7_0`에서 다운로드 후 실제 채널 D를 수신했다.
125 MHz H11/G11 경로를 사용한 초기 시도는 UART 무출력이었으며,
공식 보드 XML의 **300 MHz AH18/AH17 경로로 변경한 후 통과**했다.
125 MHz 경로의 보드 측 세부 원인(클럭 발생기 설정 등)까지 규명한 것은 아니다.

| 검증 | 결과 |
|---|---|
| `make sim-c-demo` | PASS: RAM 합계 55, UART `C OK\n` |
| `make sim-mini-os` | PASS: timer trap 35, ECALL 430, 예상 밖 trap 0 |
| `make sim-zcu104` | 자동 부팅·warm reset 모두 PASS, 각 실행 A=82/B=54/C=27 |
| Vivado 합성·배치배선·bitgen | PASS, DRC 위반 0 |
| setup / hold 최악 slack | +2.629 ns / +0.039 ns |
| 제약 없는 내부 endpoint | 0 |
| 자원 사용 | LUT 4,479 (1.94%), FF 1,390 (0.30%), BRAM 0 |
| 실제 보드 UART | PASS: 56,456 bytes, boot banner 확인 |
| 실제 태스크 문자 수 | A=28,129, B=28,072, C=242 |
| 실제 문자 전환 | 726회, 배너 이후 A/B/C 이외의 바이트 0 |

수신을 먼저 시작하고 다운로드 완료 후 5초 동안 더 수집한 기록이다.
전체 수신 시간에는 구성 완료부터 Vivado 종료까지의 시간도 포함된다.
문자 전환 수는 UART 관측치이며 모든 context switch 횟수와 같지는 않다.

검증한 bitstream SHA-256:

```text
ca32bcf0ab0211c95cf3c2ed3e31317c75de44e0f6a72bc66af196bc5f886241
```

재빌드나 재검사 시 `build/zcu104/`의 로그와 수신 결과는 갱신된다.
위 표는 이 시점의 검증 기록이며, 최신 결과는 `uart_result.json`을 확인한다.

## MiniFS 실제 보드 검증 기록 (2026-09-29)

`make test-zcu104`로 MiniFS 비트스트림을 ZCU104 PL에 다운로드하고,
USB UART 채널 D에서 5초간 추가로 수신했다. `build/zcu104/uart_result.json`의
검사 결과는 `passed: true`, `minifs_pass: true`다.

| 항목 | 결과 |
|---|---|
| 수신 바이트 | 57,476 |
| 부팅 배너 | 확인 |
| MiniFS 생성·기록·읽기·삭제 데모 | `[MiniFS] PASS` 확인 |
| 태스크 출력 | A=28,551, B=28,536, C=246 |
| UART 문자 전환 | 861회 |
| 수신·검사 오류 | 없음 |
| bitstream SHA-256 | `6e241d955d90b6d93931ec6b17494305a3037917f3a258e0df92d44fbe99a04c` |

이 검사는 UART 출력으로 MiniFS 데모의 성공을 확인한다. RAM disk의 모든 블록을
보드에서 직접 읽어 검사하거나, 전원 차단 후 파일 유지 여부를 확인하는 검사는
아니다. RAM disk는 전원을 끄면 사라지도록 설계했다.
